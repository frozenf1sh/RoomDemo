## 二 分支和提交方式

UI开发分支：`codex/atelier-four-stage-ui`，由本次文档交付后的main建立并推送。UI同学在自己的工作目录执行：

```bash
git fetch origin
git switch --track origin/codex/atelier-four-stage-ui
git lfs pull
```

如果本地已经有该分支，切换到它后用`git pull --ff-only`更新。开始前先确认自己的未提交改动；不要用强制重置来切分支。Unity入口为`Assets/_Game/Content/Scenes/AtelierPlayable.unity`，预览UI用下文独立场景。正式Build Settings保持原样。

冻鱼与Codex的实现分支为`codex/atelier-scene-flow`，已经从同一文档基线开始实现。两条线向main分批合并，再各自同步main，不直接互相修改对方工作分支。UI分支可反复提交PR，不等全部界面做完才第一次交付。

每个PR围绕一个可演示结果，附运行方式、改动Prefab、接口变化和实际检查记录。提交前用`git diff --cached --name-only`核对范围，不提交Library、Temp、本地Logs或无关ProjectSettings。界面改完随Prefab一起交，不只提交截图。

## 四 首批就固定的接口合同

这里固定语义和字段，首批UI提交可据此建立`Contracts`与Fake实现；具体C#类型沿项目命名规范，不另建通用框架。新字段先同步本文与04，再改两边代码。UI的展示数据不能成为第二份世界状态。

### 画布快照

| 字段 | 含义和所有者 |
| --- | --- |
| SessionEpoch、CanvasRevision | 会话世代与画布版本，由应用层生成；拒绝重开后或改画前的旧请求 |
| LayerId、BrushId、PreviewTexture | 当前层、稳定图样ID和原始预览图，由真实适配器提供 |
| RemainingPaint、CommittedStrokeCount、PlannedStrokeCount | 本层剩余量、已落笔数、计划5或6笔，UI只读 |
| MinCost、MaxCost、SelectedCost、SelectedAngle | 本次合法区间和当前预览选择；UI可临时选值，提交由应用层复查 |
| CanUndo、CanFinish、FinishBlockedReason | 直接显示许可和缺项；第四层第三笔不等于可以普通定稿 |
| ToolMode、CanUseKnife、CanReturn | 工具状态和返回许可；不能靠按钮曾经亮过推断当前可用 |
| CanvasTexture、IsSubmitting | 当前真实作品和一次提交中的状态；作品纹理由我们持有，UI不释放它 |

UI发出的最少意图：`RequestCommitStroke`（世代、版本、笔触ID、归一化UV、角度、成本步）、`RequestUndo`、`RequestFinishLayer`、`RequestToolMode`、`RequestReturn`。第四阶段仍使用“完成绘画”按钮，真实适配器根据当前状态路由到普通定稿命令，UI不能自行决定结束哪一条线。

画布区域适配接口由我们提供屏幕点到实际画布UV的转换，并返回可落笔与否；UI预览时用RectTransform替身，真实场景替换为同一语义的实际表面映射。临时预览不写入GameState。每次按下松开只提交一次，成本与可见大小一致；世界合成、Alpha边缘许可和最终刀面路径效果由我们实现，UI不再维护一张独立正式作品。

### 笔记与通用UI

材料快照包含稳定ID、中文名、观察/概念/笔刷等标签、来源ID、来源缩略图和说明；灵感与已形成结果分开。界面临时选词最多三项，提交全部已选项，不能在UI暗取其中两项。来源定位请求只请场景侧聚焦已知对象，不替玩家授予物件。

组合、撤销和收层等回调返回接受/拒绝及明确原因；UI收到新快照后刷新结果，不先扣颜料再补退款。结果反馈、材料列表、笔记未读和旁白消费同一批真实事件，避免分别计数。

终局面板只接受确定的`EndingKind`和允许的菜单动作。练习回看须由应用层提供已验证恢复接口；在此之前不显示空按钮。N、Esc、右键和UI事件消费顺序按02执行，旧演出取消由我们负责，UI在OnDisable/失焦时交还指针捕获并取消本地预览。

## 五 如何最快并行交付

以UI一位开发、冻鱼与Codex一条实现线并行，复用当前星空、房间擦除和现有UI为前提，首轮排期按约6至8个有效开发日预留，属于估算。每批验收后立即合入；首个真实闭环目标放在前1至2个有效开发日，实际速度根据第一批结果滚动调整。

| 批次 | UI同学交付 | 冻鱼与Codex交付 | 一起验收的结果 |
| --- | --- | --- | --- |
| A 接口和第一层，优先级最高 | 画布Workspace、Contracts、Fake状态、原始PNG导入、独立预览场景；先保证可用 | 阶段一观察/配方、画布账本、真实RT、输入/UV适配、最少必要场景绑定 | 真正亲点来源→洗笔记录结果→合第一支笔刷→三笔提前完成/六笔耗尽；返回再进不丢画 |
| B 完整创作循环 | 笔记材料单列、三项提交、来源与提示、笔刷结果、通知；完善撤销及长文案 | 第二/三阶段、镜面比较、已有碎片、干颜料板、刀刃/刀面；局部遮挡同时接入 | 连走前三阶段，默认6/5/5笔；无重复领奖、无不明缺项、旧层保留 |
| C 第四层和双路线 | 最终工具位、完成禁用原因、两种结尾共用菜单、独立字幕和回读 | 左灯与暖星、异常持久提示、两次屋面操作、天空/笔迹/房间主动调查；复用现有星空和擦除 | 两条完整路线都能主动结束，错过闪光仍可发现，调查不误锁路线 |
| D 集成和交付 | 真实构建中的字形、窄窗口、拖动中断和点击穿透修正；菜单/回读收尾 | 主场景接线、性能/资源生命周期、音效/配音接入、完整构建和缺陷修正 | 普通线和现实线的构建证据、首次玩家问题修正、资源与许可证齐全 |

A先交功能版Prefab，视觉细节在B/C补齐；B与C能拆开提交的部分不要等所有界面完成。我们先合UI的Contracts和可编译Workspace，再绑定第一层，UI随后继续笔记本，不等待镜面和TA全部完成。不要让两边各自做完整系统，最后才发现按钮和命令对不上。

第一轮关键路径是“真实画布账本与RT→一层联调→四阶段及双路线→真实构建”，不是重新画星空。当前已拆好的场景、点灯、镜头、现有擦除和固定画幅星空都按复用处理。

## 六 同步节奏和合并边界

每个有效开发日开始时同步main；中途按批次交可编译小提交；结束前在同一构建确认一次目前最远可走到哪。阻塞信息只需包含步骤号、实际输入、结果、预期和截图/日志定位，不用等日报汇总才提。

UI PR按“合同与预览→画布操作→笔记本→结尾与适配”拆；场景流程PR按“规则与第一层→物件及中间阶段→第四层及路线→TA与视听收尾”拆。只有main上的已合入提交作为下一次联调基线；更新分支优先正常合并main，避免重写另一位已经拉取的分支。

若必须改共享合同，先在PR明确新增字段、默认值和兼容方式，使旧调用方仍能编译，再替换调用点。一次只由一个人修改同一Prefab；主场景由我们保存，UI母版由UI同学保存。meta与资产一起提交，不移动GUID、不手工解决复杂场景YAML。

## 七 开发前就要并行补齐的素材

由冻鱼协调策划/美术提供催稿便签正式全文、符合原稿的蜡笔画正面、模型来源许可、所需配音和手部握持资源。当前蜡笔画包的褐色人物画与原稿不符，不能作为奔放观察的最终证据；镜面需要实际渲染，不能把扫描贴图视为已经可用。

功能开发可先使用已明确标注的现有便签、纸模占位和原稿字幕，不卡住UI和规则联调；全素材交付前仍要替换、接入并实际复查。自然接触Foley、角色配音、手部握持和真人鼠标验收全部列入收尾清单，缺项必须记录，不把功能试玩包称为全素材验收通过。

## 八 两个交付门槛

**功能试玩包。** 四阶段与两条路线全部可走；至少三笔及末笔范围有效；动作结果自动收录；玩家作品保留；无流程阻塞和运行错误；中文在真实构建可读；试玩包内明确记录尚缺素材。

**完整交付。** 功能试玩包的缺陷修正完成，催稿正文、蜡笔画、手部、接触声音和配音等约定素材接齐；最低分辨率和全部输入中断检查完成；首次玩家验证过关键动机和反馈；普通/现实路线各有连续操作记录及实际构建版本；来源与字体许可证随包提供。试过的内容和未验证内容分别记录，不能以自动事件回放代替真人验收。

优先处理阻塞、误锁路线、误扣颜料、丢笔触和看不见反馈的问题，再做不影响理解的细节润色。现实路线始终沿用当前星空材质与运行表现。
