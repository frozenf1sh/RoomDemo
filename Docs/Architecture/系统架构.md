# 系统架构

## 分层

```text
Game.Domain       事实、ID、规则、配方和反应；不引用 Unity
      ↑
Game.Application  GameSession 与游戏用例；不引用 Unity
      ↑
Game.Unity       输入、UI、场景组件、Presenter 和演出
      ↑
Game.Editor      UnityEditor 工具；生成和检查场景资源
```

Unity 侧接收输入，向应用层提交命令。应用层调用领域规则并发布事件；Presenter、UI 和演出读取结果。逻辑上的核心在 Domain，Unity 是外层适配。

完整运行链见[系统数据流图](系统数据流.drawio)。

## 关键边界

- `GameState` 是唯一世界事实来源。Transform、材质和 GameObject 的显隐不是游戏状态。
- `RuleEngine` 负责通用发现、组合、条件和反应闭包。具体玩法放在 `Runtime/Domain/Rules/` 的内容规则表中。
- `GameSession` 是 Unity 代码与规则之间的入口。它接收观察、组合、场景动作和明确的日序命令，再发布 `DomainEvent`。
- UI 只保存当前选中的词条。Presenter 只读事实、更新画面，不修改状态，也不互相调用。
- 演出系统只处理时间、声音和画面。事实立即由规则成立，动画可以随后播放；重开或预设切换时要取消旧演出。
- 绘画强度、天空流速等参数只属于表现层，不进入 `GameState`。
- 领域和应用程序集不依赖 `UnityEngine` 或 `UnityEditor`。Editor Builder 通过 `AssetDatabase` 更新场景与资源，不进入运行时程序集。
- 交互物体的逻辑身份与视觉资源分开。换模型不改变稳定 ID。

## 新增玩法

1. 在 Domain 定义稳定 ID、发现、观察、配方和反应。
2. 在 Application 的会话用例中添加确有必要的玩家命令。
3. 在 Unity 场景配置交互目标，由输入组件提交命令。
4. 让 Presenter 响应领域事件；不在 `Update` 中判配方或写事实。
5. 为领域／应用逻辑运行相关测试；场景和美术改动在 Unity 中运行并检查 Console。

新画室规则位于 `AtelierRules`，早期通用画室规则位于 `StudioRules`，旧主线内容位于 `MainlineRules` 与 `NarrativeRules`。修改前先确认场景实际绑定的是哪张规则表。

## 四阶段首批接入（2026-10-19）

`AtelierFlowRules.CreateOpening()`定义P00至P07，`AtelierFlowGameplay`在AtelierPlayable装配这一会话，旧静物输入停用。`GameState.AtelierCanvas`是唯一作品和颜料账本；应用层以会话世代、作品版本和笔触ID验证提交、撤销和主动收层，再整批发布事件。Unity的`AtelierFlowCanvas`只从已确认笔触重建作品RT，并负责原始PNG有效Alpha的画外许可与预览，UI不保存第二份正式作品。

SceneAction可声明必须亲点的附加来源与当场产生的Observation；规则校验拒绝物体和完整概念产出，洗笔事实与结果在有效接触同一命令成立。纯视觉底稿通过阶段适配读取结果，不写事实。二至四阶段的内容和双路线尚未接入；现有API、UI接法与运行边界见[12 实施记录](<../Design/全流程重设计20261019/12 主流程首批实施记录.md>)。

2026年10月20日：便签阅读成为可选动机说明，不再作为首层发现/洗笔的前置；N01结束只由Unity场景层交回输入，不伪造阅读事实。UI接手现有画布命令与RT，用Workspace开关停用占位输入，用NotebookBackHandler先消费导读/详情返回；UI不再做正式账本。更新分工见13。
