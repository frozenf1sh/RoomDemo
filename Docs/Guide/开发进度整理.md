### 画室里没有日序

实测：`AtelierRules` 的 4 条反应 `DelayDays` **全部为 0**，`AtelierGameplay` 中 **`Session.AdvanceDay()` 没有任何调用方**，因此画室玩法里 `GameState.DayIndex` 恒为 1，`NarrativeStage` 中与日序相关的分支不会触发。

这是内容设计的有意结果（两条路线都在同一夜内完成），但意味着 `PendingDeferredEffect` 与日序推进机制在画室玩法里是**未被使用的代码路径**——只有旧主线（`NarrativeRules` 的 `canvas-opens-next-day`、`growth-opens-next-day`，delay 1）才用它。维护时不要把日序当成当前玩法的一部分。

## 五、两条收束路线

从**同一个空白画布**开局，不弹选路线窗口；路线由玩家实际操作形成。

### 共同开场

读便条 → 依次亲点杯／笔／灯／窗并在画布上落笔（有限笔数，非自由绘画）→ 实体洗笔（笔毛入水约 4.2 秒）→ 亲点水得"散开的水纹"→ 组合成"流动"→ 应用到画里的水；
实体划火柴 → 送到灯芯 → 点灯 → 亲点灯得"亮起的灯芯"→ 组合成"点亮"→ 应用到画里的灯；
实体拉绳收帘（约 4.8 秒）→ 亲点布褶得"拉开的窗帘"→ 组合成"打开"→ 应用到画里的窗。

完成后进入 `ready_to_deliver`，但**不会自动结束**，也不提前锁住笔记本。

### 路线 A：主动定稿

前提：画内三解释完成，**且从未把画法用于现实**（洗笔、点灯、拉帘属于普通实体操作，不算偏离）。

近看画布 → 点"就交这张" → `canvas_delivered`。画留在画架晾干；世界解释停止；**不出现坏结局或嘲笑文案**。
稳定事实 ID 沿用 `atelier.canvas_delivered`。

### 路线 B：把画法用于画室

从共同开场即可分出；一旦发生过一次现实解释，本局**不会**再回到普通定稿收束（`deliver` 被 `reality_touched` 阻断）。

真实杯水（流动+杯里的水）→ 擦湿色学"擦除"（从左向右实体拖擦）→ 擦开屋顶中央（约 7.5 秒，先露普通黑夜）→
亲点真正露出的夜空得"天空" → 点亮+天空 与 流动+天空（可换序，两者齐才成完整星夜）→
等约 5 秒出现跨材质的接连笔迹 → 亲点笔迹 → 向右转头亲点整间画室墙面得"房间" →
擦除+房间 → 约 16 秒全房间统一笔势擦除（同一世界笔刷场经过梁、墙、窗框、玻璃、帘褶、吊带、器物、画架、地板与窗外实体景物），灯光在笔势到达后才熄去，最终只剩运行时流动星夜。

**关键约束（都有测试守住）**：屋顶显露、完整星夜和笔迹观察都**不会自动授予"房间"**；没有那一次单独点击，最终配方不能成功。

## 六、架构现状

### 分层与约束（文档与代码一致）

依赖方向仍为 `Game.Domain → Game.Application → Game.Unity`，`Game.Editor` 独立。领域与应用层均 `noEngineReferences: true`。
`Game.RealtimePainterly` 是**表现层旁支**：只引用 URP 与 InputSystem，**不引用 Domain/Application**——绘画强度、天空流速等参数无法进入 `GameState`，这在程序集层面被强制。

### 双入口并存（重要）

仓库里现在有**两套并行的运行时入口**：

| 入口 | 场景 | 规则表选择 | 状态 |

### 两个画室场景的父子关系

`AtelierPlayable` 不是独立美术，而是从 `AtelierNight` **另存 + 逐轮增量安装**的产物：

- `AtelierGameplayBuilder.BuildStageOne()` 强制要求当前活动场景是**已保存的** `AtelierNight`，且**若 `AtelierPlayable` 已存在就直接抛异常**——只允许增量修正，禁止重新生成。
- 另存后会把 URP 管线资产**克隆一份**（`画室玩法专用管线.asset`，`OnlyOwnPipelineAtRuntime = true`），避免持久污染共享的质量设置；并销毁基线里的 `AtelierBuildEvidence` 取证组件。
- 后续 `AtelierCurtainRevision` / `AtelierLampRevision` / `AtelierFinaleRevision` / `AtelierOpeningRevision` / `AtelierFinishing` / `AtelierPolish` 都只对 `AtelierPlayable` 做增量，且会拒绝非该场景的活动场景。
- 体量差（`AtelierPlayable` 3.79 MB / 138,571 行 vs `AtelierNight` 3.12 MB / 113,765 行，另 3.12 MB / 106,336 行为归档的 `DemoRoom`）就是玩法增量：19 个交互 Logic 子节点、独立洗笔工作簇、任务画、笔记纸面与取证组件。

这条"另存 + 增量修正、禁止重建"的约定执行得很彻底，是上一版报告里"表现层安装器无法一键重建"问题在画室阶段的改进版本。

### 全房间统一笔势擦除的实现方式

值得单独记录，因为它是本轮最重的表现技术：

- 表现入口 `AtelierFinalePresenter` 在 `Bind` 时把 ArtRoot/GameplayRoot 下**所有 Renderer 换成 6 种擦除 Shader 的运行时克隆**（`ErasureLit/Paper/Water/Painting/Flame/Terrain`），用 `_AtelierEraseGroup`（0 普通 / 1 屋顶 / 2 窗框）区分分组；原材质只在运行时克隆，销毁时恢复并释放。
- 节拍：屋顶 7.5 秒、窗框 5.5 秒、接连笔迹 5 秒、**全房间 16 秒**，各写全局量 `_AtelierRoof/_AtelierFrame/_AtelierMark/_AtelierRoom`。
- C# 的 `AtelierFinalePresenter.RoomOrder(p)` 与 `AtelierErasureField.hlsl` 的 `AtelierRoomOrder(p)` 是**同一公式**，用于让拾取屏蔽与着色器擦除顺序一致。
- 输入随擦除失效：`Pick()` 逐层跳过已被擦掉的屋顶、屋顶未落稳时的天空、`_AtelierMark < .99` 的笔迹、未亲点的房间、已擦掉的窗框。

### 求值顺序（相对上一版的变化）

```
命令分发（RuleEngine.Execute）
  ├─ InspectObject / ObserveDetail / Combine / PerformSceneAction / AdvanceDay / Interpret（旧）
  ├─ 仅当命令被接受，进入事实闭包 EvaluateReactions
  │    do { 逐条扫描；未触发且前置成立 → 先 Fire 再产出 } while (有触发)
  │    DelayDays == 0 → 立即产事实
  │    DelayDays > 0 → 只 Schedule 到 DayIndex + DelayDays
  └─ 返回只读事件
```

新增的约束点：
- `Combine` 在配方命中后先检查 `state.Allows(recipe.Disposition)`；锁入画布后远离画布的偏离解释会被拒绝（理由文案："先把画中最后的天空补完。"）。
- `Act`（现场动作）要求来源可调查、`Requires` 全成立、`Blocks` 全不成立、且 `!state.CanvasLocked`。
- `Complete(recipeId, disposition)` 先去重后计数——重复提交不刷服从／偏离。

**四种控制手段共同保证"亲点"原则**：`Inspect` 只看 `DiscoveryRule.Requires`；`ObserveDetail` 额外要求 `state.Knows(source)`；`PerformAction` 只认 `SceneActionRule` 且不吃动画状态；`Combine` 走配方匹配。演出、便条、动画都无法替玩家写状态。

## 十、缺口与风险

### A. 验收缺口（最重要，未变）

1. **真人鼠标操作验收始终未完成**。各阶段记录反复写明原因：复测时 Mac 锁屏、原生窗口工具返回 `noWindowsAvailable`，因此**只用显式命令、射线拾取和 UI 事件回放**验证，并明确"不得写成真人鼠标试玩通过"。
2. **手部握持未制作**：火柴没有手部模型／握持遮挡，返回主视角只结束手持输入。**接触 Foley 与角色配音未制作**。
3. **独立静物画按用户要求暂缓**：保持前轮"现场短笔触重绘"版本，未重做为画师新绘作品。
4. **旁白听感、首次理解度、操作直觉未验收**；`PLAYTEST.md` 明确"当前没有陌生玩家的有效答卷"。
5. 完整成画**偏暗**，需真人复核局部亮色可读性（文档自述）。

### B. 结构性风险

6. **正式构建入口不含玩法**。`EditorBuildSettings` 只启用 `AtelierNight.unity`，而该场景只有 4 个项目脚本（相机、星夜、美术状态、构建证据），没有 `AtelierGameplay`。在 Unity 中直接 Build 得到的是不可玩的美术包。文档把它写成有意约定（开发副本与正式入口分开维护），但目前**没有任何"正式可玩入口"**——若要交付可玩包，必须依赖 `AtelierGameplayBuild.BuildMac()` 这类显式入口。
7. **画室主流程零 PlayMode 覆盖**。29 项 PlayMode 测试虽然**全部通过**（本机实跑 104.9 秒），但它们全部针对归档场景 `Archive/DemoRoom.unity`；画室玩法的"输入 → 场景对象 → Presenter"这条链没有被自动化验证，只能靠现场观察与 `--atelier-flow-review` 取证回放。这是当前最值得投入的工程缺口（见 P0-2）。
8. **`Game.RealtimePainterly` 是 `Game.Unity` 的硬依赖**。同时 `AtelierGameplayBuild` 会在构建期临时改写 URP GlobalSettings、`GraphicsSettings.defaultRenderPipeline`、`QualitySettings.renderPipeline`、`PlayerSettings` 应用标识，然后恢复。这类"构建期改全局状态"的模式较脆弱（文档也记录了"构建期间 URP 自动清空了全局资源列表，已用备份恢复"）。
9. **构建目标硬编码 macOS**：`AtelierPreviewBuild.BuildMac` 与 `AtelierGameplayBuild.BuildMac` 都写死 `BuildTarget.StandaloneOSX`。本机是 Windows，这两个入口不能直接用。
10. **构建入口按阶段复制**：`QueuePhaseBuild` / `QueueOpeningBuild` / `QueueLampBuild` 各自硬编码输出目录名（`AtelierOpening_20261011`、`AtelierLight_20261011` 等）。每阶段加一个入口，长期看难以维护。
11. **旧路径仍在编译**：`AtelierRules` 复用了 `StudioRules` 的稳定 ID，但 **`StudioRules.Create()` 在运行时没有任何调用方**（只有它的静态 ID 被引用）。`MainlineRules` / `NarrativeRules` / `DemoRules` 同样只被归档场景与旧测试使用。这些表会持续参与编译与维护。
12. **仓库体积**：`Assets/` 575 MB、`.git` 754 MB。`ArtRebuild` 单目录 488 MB，其中包含扫描模型与 2K/4K 贴图。`Tree Small 02` 自述原模型约 177.7 万顶点且未做 LOD。
13. **画室路线的日序机制是死路径**：4 条 `atelier.reaction.*` 的 `DelayDays` 全为 0，`Session.AdvanceDay()` 无调用方（见第四节）。属有意设计，但会让读者误以为日序仍是玩法的一部分。
